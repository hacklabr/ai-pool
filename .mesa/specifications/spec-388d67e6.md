# Especificação Técnica: AI Provider Pool — Proxy OpenAI-Compatible

## 1. Sumário Executivo

O **AI Provider Pool** é um proxy/load-balancer compatível com a API OpenAI que centraliza e governa o acesso a múltiplos provedores de LLM (Gemini, Mistral, DeepSeek, Z.ai, Kimi). O sistema distribui carga entre chaves de API do mesmo provedor, garante resiliência via failover transparente, aproveita cache de contexto dos LLMs via afinidade de roteamento, e desabilita automaticamente chaves problemáticas reativando-as quando a cota é liberada.

**Problema resolvido:** membros da equipe ficavam sem tokens em seus planos enquanto outros tinham saldo ocioso; chaves eram compartilhadas inseguramente via Telegram. O pool elimina ambos os problemas com distribuição inteligente de carga e governança por usuário/token.

**Stack:** Go + Beego (admin/UI) + HTTP puro (proxy core) + PostgreSQL. Deploy em Docker Compose (local) e Kubernetes + Helm (produção). Licença MIT.

**Escala-alvo do MVP:** ~30 usuários, ~5 provedores, 1–5 chaves por provedor.

## 3. Decisões Técnicas Consolidadas

> Todas as decisões abaixo foram aprovadas por consenso unânime (6-0) dos especialistas após 3 turnos de discussão.

### 3.1 Arquitetura Geral

#### 3.1.1 Arquitetura Hexagonal (Ports & Adapters)
O sistema adota **arquitetura hexagonal**:
- **`domain/`** — lógica de negócio pura, sem dependências de framework ou infraestrutura.
- **Adapters** — Beego (transporte HTTP admin/UI), net/http puro (proxy), PostgreSQL (persistência), memoryStore (estado).
- Interfaces abstraem stores para permitir troca de implementação (in-memory → Redis) sem reescrever o hot path.

#### 3.1.2 Separação de responsabilidades
- **Proxy Core** (net/http puro): roteamento, load balancing, failover, streaming. Não roteia pelo Beego (que pode bufferizar e quebrar SSE). Handler HTTP puro com `http.Flusher`.
- **Admin/UI** (Beego): gestão de usuários, provedores, chaves, dashboard. Controllers + partials HTMX + JSON isolado para gráficos.
- **API do proxy**: exposta sob `/v1/*` (compatível OpenAI). **Admin API/UI**: sob rotas dedicadas.

#### 3.1.3 Réplica única em produção (Opção A)
- **MVP roda com 1 réplica** (`replicas: 1`), `memoryStore` para LRU/afinidade/rate-limit, **sem Redis**.
- Justificativa: elimina TODA a classe de bugs de estado distribuído (rate limit ×N, afinidade fragmentada, invalidação de cache de token). Adequado para 30 usuários sem SLA.
- **Zero-downtime planejado** via `RollingUpdate` com `maxSurge: 1` / `maxUnavailable: 0` + graceful shutdown.
- **Risco aceito:** perde-se HA em falha não-planejada do pod (segundos de restart).
- **Gatilhos documentados para migrar à Opção B (≥2 réplicas + Redis mandatório):** SLA duro, RPS sustentado > 50/s, quotas distribuídas, ou multi-tenancy real.
- **Store abstrações no MVP:** interfaces `LRUStore`, `AffinityStore`, `RateLimiter`, `TokenCache` definidas desde o MVP, mas apenas `memoryStore` implementada. **Não importar `go-redis`** (evita dep fantasma). A troca futura é adicionar uma implementação Redis.

#### 3.1.4 Multi-tenancy preparado (não implementado)
- `organization_id NOT NULL DEFAULT 1` em TODAS as tabelas desde o MVP.
- Default org (id=1) representa o tenant único do MVP.
- Índices composite com `organization_id` à esquerda; queries sempre filtram por ele; regra de lint no repo.
- Tabelas standalone (teams, quotas, time_window_limits) **deferidas** para o roadmap — o `organization_id` já pavimenta a relação mais cara.

### 3.2 Proxy Core (núcleo do produto)

#### 3.2.1 Proxy OpenAI-compatible (repasse transparente)
- Repassa requisições aos provedores preservando os **bytes originais do body**. Decisões de roteamento usam parse parcial do payload.
- **HTTP client único global** com connection pooling; sem `Client.Timeout` global (controle via `context`).
- **Override de User-Agent:** quando configurado por provedor/chave, substitui o header antes do repasse.
- **Streaming SSE (`stream: true`):**
  - Repasse chunked com `http.Flusher` e flush imediato a cada chunk.
  - **3 timeouts:** first-byte (até primeiro chunk útil), idle (entre chunks), overall.
  - Propagação rigorosa de `r.Context().Done()` — se o cliente desconecta, cancela o upstream (poupa tokens).
  - **Sem failover transparente após o primeiro chunk útil** do stream (após começar a responder, não se pode tentar outra chave).

#### 3.2.2 Load balancing LRU + Afinidade de cache de contexto
- **LRU (Least Recently Used):** entre as chaves habilitadas de um provedor, seleciona a menos usada recentemente. Rastreio em memória (map + mutex). É heurística — sem persistência obrigatória.
- **Afinidade de cache de contexto** (diferencial do produto):
  - **Mecanismo primário:** header opt-in `X-Conversation-ID`. Se presente, roteia para a mesma chave usada anteriormente naquela conversa.
  - **Mecanismo fallback (sem header):** hash SHA-256 do prefixo normalizado das mensagens. Continuidade definida como "o array de mensagens anterior é prefixo estrito do atual" (`n > k`).
  - **Store POR usuário** com TTL (30 min) + LRU eviction.
  - **Best-effort, em memória** — se a chave alvo estiver desabilitada, cai para LRU normal.
  - **Segurança:** o hash de afinidade **jamais aparece em logs/métricas/traces**; preferir `X-Conversation-ID` (não derivado de conteúdo). Não persistir fingerprint.
  - **Edge cases:** primeira mensagem (sem prefixo) → LRU normal; mensagens idênticas de usuários diferentes → store por usuário isola.
- **Atomicidade sob concorrência:** mutex protege o map de estado; 30 usuários com requisições simultâneas é trivial para a granularidade.

#### 3.2.3 Cadeia de failover
- Ao receber erro de uma chave, tenta a **próxima chave do mesmo provedor**, mesmo modelo.
- **Tenta TODAS as chaves habilitadas do provedor** antes de retornar o erro ao cliente.
- **Classificação de status codes:**
  - **NÃO disparam failover:** 400 (bad request — problema do cliente), 404, 413 (payload grande).
  - **DISPARAM failover:** 401/403 (auth — embora possa indicar chave inválida), 429 (rate limit), 5xx (erro do servidor), erros de rede/timeout.
- **Retry com backoff exponencial + full jitter** entre tentativas. Parâmetros configuráveis (base, cap, max retries implícito = nº de chaves).
- **Failover como orquestrador stateful externo ao pipeline** (não como policy do pipeline) — mantém o estado de quais chaves já foram tentadas nesta requisição.

#### 3.2.4 Auto-disable de chave com parse de data
- **Gatilho:** chave atinge N erros em janela de tempo → desabilitada.
- **Parse da mensagem de erro:** busca data de liberação de cota (vários provedores informam na mensagem).
  - **Registry extensível por provedor:** interface `ErrorParser` + implementação por provedor + `DefaultErrorParser` (fallback regex genérico). Adicionar parser de novo provedor = implementar a interface.
- **Reativação automática** na data informada pelo provedor (`disabled_until` timestamp persistido + scheduler + lazy reativação).
- **Se o parsing falhar:** a chave entra no fluxo de retry com backoff crescente (não bloqueia o pool).
- **Persistência:** `disabled_until` em PostgreSQL + scheduler periódico + reativação lazy (na próxima tentativa de uso, se a data passou, reativa).
- **Estado da chave (4 estados visuais na UI):** ativa, desabilitada manualmente (admin), auto-desabilitada com reativação agendada, em backoff.

#### 3.2.5 Rate limiting por usuário/token
- **Algoritmo:** token bucket, abstraído via interface `RateLimiter` (in-memory no MVP).
- Limite configurável (ex.: req/min) por usuário/token.

#### 3.2.6 Registro de uso e auditoria
- **Logging assíncrono** fora do path crítico: via canal bufferizado + batch insert.
- Captura por requisição: **quem** (user/token), **qual** chave/provedor/modelo, **quantos tokens** (prompt/completion/cached), **latência**, **status**, **quando**.
- **Durabilidade:** WAL é a garantia real; perda máxima aceitável em crash de pod ~25-50 logs (1-2 batches em trânsito); dead-letter protege de falha de INSERT.

### 3.3 Segurança

> Mentalidade orientadora: **o sistema é um cofre de chaves com API**, não um proxy qualquer.

#### 3.3.1 Modelo de ameaças
- **Ativos protegidos:** chaves de API de provedores (altamente sensíveis), tokens de usuários, dados de uso.
- **Boundaries de confiança:** cliente ↔ proxy (token), proxy ↔ provedor (chave), admin ↔ DB.

#### 3.3.2 Chaves de provedores (armazenamento)
- **Envelope encryption:** AES-256-GCM no DB, com KEK (Key Encryption Key) **externo ao DB**, injetado via ESO como **arquivo readOnly** (não env var).
- `encryption_key_id` por chave para rotação.
- Nunca plaintext; redação centralizada em logs via `SanitizingLogger`.

#### 3.3.3 Tokens de API dos usuários (estilo `sk-...`)
- **Formato:** `sk-aipp-AB12CD34-••••` (prefixo `sk-aipp-` para GitHub Secret Scanning, `key_id` público, secret mascarado). Mostrado completo apenas uma vez na criação.
- **Hashing:** **HMAC-SHA256 + pepper externo** (defesa em profundidade contra dump do DB). `key_id` separado para lookup O(1).
- **NÃO usar Argon2id/bcrypt para tokens** (funções lentas; o salt quebra lookup O(1); tokens de alta entropia não precisam).
- **Validação:** **DB hit por request** (sem cache positivo). Para 30 usuários, latência sub-ms é ruído vs LLM call. Garante **revogação instantânea e determinística** ao desabilitar/excluir usuário.

#### 3.3.4 RBAC
- **Roles:** `admin` (gerencia provedores, chaves globais, usuários) e usuário comum (consome via seus tokens, vê próprio uso).
- **Default-deny** com middleware obrigatório em cada endpoint.
- **Duas cadeias de auth segregadas:** Bearer `sk-aipp-...` (proxy `/v1/*`) vs Session httpOnly+CSRF (admin UI).
- **Princípio do menor privilégio** em toda a admin API.

#### 3.3.5 Autenticação de usuários (login web)
- **Senhas:** Argon2id.
- **Proteção brute-force:** rate limits explícitos em `/login`, criação de token, mutações admin.
- **Sessão:** cookie httpOnly + CSRF token.
- **OAuth:** roadmap (configurável qual método). Login multi-step desenhado desde já para absorver MFA/OAuth futuros sem redesign.

#### 3.3.6 Segurança do proxy
- **SanitizingLogger:** redação centralizada — chaves de provedores jamais aparecem em logs/respostas de erro.
- **Sanitize headers** repassados.
- **SSRF guard:** validação/allowlist de `base_url` dos provedores (IP blocklist + allowlist de hostnames).
- **Validação de input.**
- **NUNCA logar conteúdo de mensagens.** Hash de afinidade só em memória.

#### 3.3.7 Auditoria e conformidade
- **audit_log append-only** (via DB grants, sem UPDATE/DELETE).
- **LGPD:** hashing de IPs em logs; proibição default de logar conteúdo de mensagens.
- **Prefixo `sk-aipp-`** registrado no GitHub Secret Scanning.
- `organization_id NOT NULL DEFAULT 1` previne leak silencioso cross-tenant (queries sempre filtram).

### 3.4 Modelo de Dados (PostgreSQL)

#### 3.4.1 Entidades do MVP (~11)
1. **`organizations`** — tenant (id=1 = default org do MVP).
2. **`users`** — id, organization_id, username, password_hash (Argon2id), role, status (active/disabled), created_at, etc.
3. **`api_tokens`** — id, user_id, key_id (público, lookup), token_hmac (HMAC-SHA256+pepper), name, status, last_used_at, created_at, expires_at.
4. **`providers`** — id, organization_id, name (Gemini, Mistral...), base_url (com SSRF guard), default_user_agent_override, status.
5. **`provider_keys`** — id, provider_id, encrypted_value (AES-256-GCM), encryption_key_id, status (active/disabled/auto_disabled), disabled_reason, disabled_until (reativação agendada), last_used_at, error_count.
6. **`models`** — id, provider_id, name (modelo), model_aliases (JSONB — aliasing p/ roadmap), model_pricing (colunas nullable — custo p/ roadmap).
7. **`rate_limits`** — id, scope (user/token), limit_value, window, etc.
8. **`usage_logs`** — particionada mensal (ver 3.4.2). FK lógica (não física) + soft-delete.
9. **`usage_rollups`** — agregações horário/diário em **tabelas** (não materialized views), com `cached_tokens` para KPI "tokens economizados por cache de contexto".
10. **`audit_log`** — append-only.
11. **`organization_id`** presente em todas as tabelas relevantes (NOT NULL DEFAULT 1).

> **Tabelas deferred (roadmap):** `teams`, `team_memberships`, `quotas`, `time_window_limits`. O `organization_id` já pavimenta o caminho.

#### 3.4.2 usage_logs em alto volume
- **Particionamento declarativo mensal** com pré-criação de partições (pg_partman ou CronJob).
- **Retention:** DROP de partição (ex.: 90 dias).
- **Rollups** horário/diário como tabelas para dashboard em ms.
- **Insert assíncrono em batch** fora do path crítico + dead-letter para falhas de INSERT.

#### 3.4.3 Indexação
- Lookup de token: índice em `key_id` (O(1)).
- Dashboard: índices em rollups por usuário/provedor/período.
- Scheduler: consulta "chaves a reativar agora" via `disabled_until`.
- Índices composite com `organization_id` à esquerda.

#### 3.4.4 Concorrência e consistência
- Scheduler de reativação: `FOR UPDATE SKIP LOCKED`.
- Transições de estado de chave (`enabled → auto_disabled`): write-through imediato (in-memory para contadores de erro, DB para transições).
- Config admin: locks otimistas (`version`).
- `last_used_at`: debounce 60s (evita write amplification).

#### 3.4.5 Migrations e operação
- **golang-migrate** via Helm Job hook no deploy.
- **Managed DB default** (CloudSQL/RDS) com backup + PITR (Point-in-Time Recovery) **inegociável**.
- **CNPG (CloudNativePG)** como exceção para on-prem.
- Replica para leitura (futuro).

### 3.5 Infraestrutura e Deploy

#### 3.5.1 Docker (desenvolvimento/teste local)
- **Dockerfile multi-stage** para Go. Imagem final: **`distroless/base-debian12:nonroot`** (precisa CA roots para HTTPS com provedores — NÃO usar `distroless/static`).
- **docker-compose.yml:** app + PostgreSQL (+ estado em memória, sem Redis no MVP). Hot reload em dev. Volumes para persistência de DB em dev. Healthchecks.

#### 3.5.2 Helm Chart (produção em Kubernetes)
- **Deployment:** `replicas: 1` (Opção A). Sem HPA/PDB/topologySpread no MVP (inúteis com 1 réplica).
- **Probes:** startup/liveness/readness (`/healthz`, `/readyz`).
- **RollingUpdate:** `maxSurge: 1` / `maxUnavailable: 0` (zero-downtime planejado).
- **Graceful shutdown** no MVP: captura SIGTERM, drena conexões, cancela streams em andamento com propagação ao upstream. `terminationGracePeriodSeconds` ajustado.
- **Service + Ingress:** annotations críticas para streaming SSE (`proxy-buffering off`, timeouts longos). Path routing serve proxy (`/v1/*`) e admin/UI.
- **ConfigMap:** config não-sensível. **Secret:** dados sensíveis de infra (DB password).
- **External Secrets Operator (ESO):** KEK injetado como arquivo readOnly. Chaves de provedores ficam **cifradas no DB** (não como secrets de infra).
- **NetworkPolicy:** egress 443 aberto para provedores, com SSRF guard interno.
- **golang-migrate:** Job hook pré-deploy.
- **readOnlyRootFilesystem: true** (compatível com embed.FS).

#### 3.5.3 CI/CD
- **GitHub Actions:** build → test → security gates (gosec, govulncheck, trivy) → image → push → deploy via Helm (push-based).
- OIDC para auth com cloud. Registry com tags/versão.

#### 3.5.4 Observabilidade
- **Logging estruturado (JSON)** com SanitizingLogger (redação).
- **Loki + Fluent-bit + Grafana.**
- **Prometheus instrumentation** incluída no código, mas **endpoint `/metrics` desativado no MVP** (ativar no roadmap).
- Tracing preparado.

### 3.6 Frontend (Interface Web)

#### 3.6.1 Abordagem: Server-rendered (NÃO SPA)
- **Beego templates + HTMX + Alpine.js + Apache ECharts.**
- Justificativa: 30 usuários internos, escopo admin CRUD-heavy. SPA introduziria toolchain bifurcado, JWT-in-localStorage (vetor XSS), estado client desnecessário. Binário Go único com `embed.FS` simplifica o Helm chart e reduz superfície de ataque.
- **Vendor-commit** (sem Node toolchain obrigatório); apenas gráficos consomem JSON; todo o resto é HTML sobre o wire via HTMX (estado no servidor, onde PostgreSQL é a verdade).

#### 3.6.2 Áreas da UI (8 telas)
1. **Login** (multi-step — absorve MFA/OAuth futuros sem redesign).
2. **Dashboard** (KPI de `cached_tokens` — "tokens economizados por cache de contexto").
3. **Gestão de usuários** (CRUD, roles).
4. **Gestão de provedores** (CRUD).
5. **Gestão de chaves** (CRUD, enable/disable manual, 4 estados visuais: ativa, desabilitada manual, auto-desabilitada com reativação agendada, em backoff; override de User-Agent).
6. **Meus tokens** (usuário gera/revoga seus `sk-aipp-...`).
7. **Meu uso** (visão do próprio usuário).
8. **Auditoria** (audit_log append-only).

#### 3.6.3 Dashboard de utilização
- Gráficos via ECharts consumindo **endpoint JSON que consulta rollups** (nunca logs crus).
- KPI destacado: "tokens economizados por cache de contexto" (rollups com `cached_tokens`).

#### 3.6.4 Design system
- **CSS:** ITCSS + BEM com namespacing (`o-`, `c-`, `u-`, `is-`). Tokens em 3 camadas (global → alias → component). Dark mode via `[data-theme]`.
- **Acessibilidade:** WCAG. Responsividade.

#### 3.6.5 Auth no frontend
- **Sessão httpOnly+CSRF** para UI (segregada do Bearer `sk-aipp-...` do proxy). AuthFilter ramifica por rota.
- Proteção de rotas admin.

#### 3.6.6 Empacotamento
- `//go:embed` no binário Go único. Servido pelo próprio Beego. Compatível com `readOnlyRootFilesystem: true`.

#### 3.6.7 Extensibilidade (roadmap)
- Multi-tenant: middleware + slot no topbar + namespace de rotas futuro (preparação barata, não quebra).

## 4. ROADMAP (considerado nas decisões de arquitetura)

> Estes itens NÃO estão no MVP, mas as decisões acima foram tomadas para **facilitar sua implementação futura**.

- **Modelo "auto"** (roteamento cross-provider/modelo por heurística) — pipeline de políticas composável prepara o terreno.
- **Failover cross-provider** — atenção ao tamanho da janela de contexto entre provedores.
- **Times** com coleções de provedores/chaves/modelos — `organization_id` pavimenta; tabelas deferred.
- **Quotas de tokens** por usuário/time/período — rollups + usage_logs preparam.
- **Limitação de horário** por usuário.
- **Multi-tenancy real** (multiorganização) — `organization_id NOT NULL DEFAULT 1` desde o MVP.
- **OAuth** configurável — login multi-step desenhado para absorver.
- **Endpoint `/metrics` Prometheus** — instrumentation já no código, só ativar.
- **Model aliasing** — JSONB em `models`.
- **Health check periódico das chaves** (probe em background).
- **Notificação/webhook** quando chave é desabilitada.
- **Custo por token** — colunas nullable em `model_pricing`.
- **Opção B (≥2 réplicas + Redis)** — store abstrações já definidas; gatilhos documentados.

### 5.5 Critérios de aceitação
1. Proxy repassa requisições OpenAI-compatible a qualquer provedor configurado, preservando payload e suportando streaming.
2. Load balancing LRU distribui entre chaves habilitadas do mesmo provedor.
3. Afinidade de cache de contexto roteia conversas contínuas para a mesma chave.
4. Failover tenta todas as chaves do provedor antes de falhar, com backoff exponencial.
5. Auto-disable desabilita chave com erros frequentes, parse de data reativa na data informada, fallback backoff se parse falhar.
6. Override de User-Agent aplicado quando configurado.
7. RBAC: admin gerencia tudo; usuário comum só consome via seus tokens.
8. Desabilitar/excluir usuário revoga acesso imediatamente (DB hit por request).
9. Registro de uso captura quem/quando/chave/provedor/modelo/tokens.
10. Dashboard mostra utilização por usuário + KPI de tokens economizados por cache.
11. Deploy funciona em Docker Compose (local) e Kubernetes via Helm Chart.
12. Graceful shutdown drena conexões e cancela streams em deploy.
13. Chaves de provedores cifradas em repouso (AES-256-GCM).
14. Tokens never logados em plaintext; SanitizingLogger redige chaves.
15. ROADMAP.md documenta todos os itens futuros.

## 6. Riscos e Mitigações

| Risco | Mitigação |
|-------|-----------|
| Beego bufferiza e quebra streaming SSE | Proxy core em HTTP puro (net/http), fora do Beego. Beego só para admin/UI. |
| Estado em memória perdido em restart (LRU, afinidade, rate-limit) | Aceito no MVP (1 réplica); store abstrações permitem migrar a Redis. Afinidade é best-effort. |
| Parsers de erro quebram ao mudar formato do provedor | Registry extensível; DefaultErrorParser fallback; falha de parse → backoff (não bloqueia). |
| Memory leak em goroutines de streaming | Context cancellation rigorosa; timeouts; revisão de código. |
| Vazamento de chave de provedor em logs | SanitizingLogger com redação centralizada; nunca logar chaves/conteúdo. |
| Perda de logs de uso em crash | WAL garanta durabilidade; dead-letter para INSERTs; perda máxima ~25-50 logs aceitável. |
| RollingUpdate com estado divergente (janela 30-60s) | 1 réplica; validar com Backend; graceful shutdown. |

## 7. Decisões Adiar/Deferir

- **Tabelas standalone** (teams, quotas, time_window_limits) — deferidas; `organization_id` pavimenta.
